## 2. 方案：只用现有 `beats`，以「哨兵行」分段

### 2.1 核心约定（纯数据，不引入任何新字段）

把第 1 关的 `beats` 由现在的 3 条扩展为 **13 条**，用两条**哨兵行**把数组切成三段：

```
beats = [ 开场段…, 哨兵-胜, 胜利段…, 哨兵-败, 失败段… ]
```

哨兵行沿用现有二元组格式，发言人固定为 `'旁白'`，文本以固定前缀开头：

| 分段 | 哨兵行 | 匹配规则（A 侧实现用） |
|---|---|---|
| 胜利段开始 | `['旁白','——若此战得胜——']` | `beat[0]==='旁白' && beat[1].startsWith('——若此战得胜——')` |
| 失败段开始 | `['旁白','——若此战不利——']` | `beat[0]==='旁白' && beat[1].startsWith('——若此战不利——')` |

各段语义：

- **开场段**（哨兵前的全部条目）：战前按现有 `storyPage()` 逐条播放，播完（或遇到哨兵）即 `startBattle`。
- **胜利段**（胜哨兵之后、败哨兵之前）：`finishBattle(b,true)` 时取用。
- **失败段**（败哨兵之后至数组末尾）：`finishBattle(b,false)` 时取用。

### 2.2 为什么哨兵行文案要写成「——若此战得胜——」

这是**零代码回退设计**：哨兵行的措辞同时满足两种读法。

- **A 已实现切片**：哨兵行被识别为分隔符，不朗读。
- **A 尚未实现切片**（零代码直接接数据）：`advanceStory()` 会把它当普通旁白念出来，此时屏幕上是「山河记：——若此战得胜——」，读起来仍是一句通顺的预演式旁白，不会出现「【胜利】」这类明显坏掉的占位符。

也就是说：**只改数据不改代码也能上线，只是胜利/失败台词会提前在战前被念完**；A 补上切片后即可变为正确行为。两段之间无需再改数据。

### 2.3 三种对话的表达方式

| 对话类型 | 承载方式 | 是否需要 A 改代码 |
|---|---|---|
| 开场触发对话 | `beats` 开场段的 5 条（第 1 条 `旁白`，后 4 条 `hero-001/009/022/003`） | **否**，现有 `storyPage()` 直接消费 |
| 胜利对话 | `beats` 胜利段的 3 条（胜哨兵之后） | **是**，见第 4 节 #2/#3/#4 |
| 失败对话 | `beats` 失败段的 3 条（败哨兵之后） | **是**，同上 |

其他现有字段的用法（全部沿用，不新增）：

- `goal` → 已在 `journey.js:16` 的 `<small>本关目标：${j.goal}</small>` 显示，保留原文案。
- `hook` → 已在 `journey.js:6` 地图详情页显示，保留原文案。
- `next` → **当前无消费点**（`01_current_anchor.md` 第 1.1 节已确认是死数据）。本方案**不动它**，也不依赖它；若 A 将来想给通关引子一个落点，可复用该字段而不必新增字段。

### 2.4 第 1 关目标 `beats` 形状（示意，完整台词见 `03_dialogue_script.md`）

```js
beats:[
  ['旁白','…开场第 1 句…'],
  ['hero-001','…'],
  ['hero-009','…'],
  ['hero-022','…'],
  ['hero-003','…'],
  ['旁白','——若此战得胜——'],
  ['旁白','…'],
  ['hero-001','…'],
  ['hero-009','…'],
  ['旁白','——若此战不利——'],
  ['hero-001','…'],
  ['hero-006','…'],
  ['旁白','…']
]
```

共 13 条：开场 5 + 哨兵 1 + 胜利 3 + 哨兵 1 + 失败 3。

> 进度条会显示 `${s.index+1} / ${j.beats.length}`（`journey.js:16`）。若 A 不做切片，玩家会看到「1 / 13」；做切片后建议把分母改成开场段长度，否则进度条会误导。这一点列入第 5 节的待决断项。

## 5. 需要 A 决断的点

1. **哨兵前缀的措辞是否认可。** 本文用 `——若此战得胜——` / `——若此战不利——`，好处是零代码回退时读起来仍通顺；若 A 更希望哨兵行绝不被误读，可改用 `【胜利】` 之类，代价是零代码回退会穿帮。
2. **进度条分母。** 不做切片时是「1 / 13」，做切片后建议改成开场段长度（「1 / 5」）。是否一并调整 `journey.js:16` 的 `${j.beats.length}`。
3. **改名风险。** `beats` 由 3 条变 13 条后，若玩家存档停在旧的 `state.story.index`（0–2），读档后仍在合法范围内，**不会越界**；但若 A 后续再缩短 `beats`，`journey.js:14` 的 `beat=j.beats[s.index]` 会拿到 `undefined` 并在 `beat[0]` 处抛错。是否顺手加一个越界保护（约 +1 行）。
4. **胜利段是否点名「鲁智深将加入」。** 现有发放逻辑是 `game.js:483–487` 的首胜判定，实际会发生；但台词若写成承诺句式会与「不得使用绝对化用语」冲突，本文按「听说有位使禅杖的好汉愿来相助」的传闻句式处理（见 `03_dialogue_script.md`）。是否接受这种弱化表述。
5. **重复进入的体力消耗。** 现状 `game.js:319` 每次进关都扣 `campaignCost`，且 `enterStory` 每次从 `index:0` 重播全量开场。本方案不解决这一点；是否纳入本轮。
